# Итерация 5. Тестирование и качество

## Цель

Закрепить работоспособность MVP автоматическими проверками, которые можно использовать в локальной разработке и в CI/CD на следующей итерации.

## Реализованные проверки

| Группа | Файлы | Что проверяется |
|---|---|---|
| Unit | `backend/tests/test_unit_rules.py` | Допустимые переходы статусов, RBAC-зависимость, доступ к заявке, формирование получателей уведомлений, mock/MAX-провайдер. |
| API | `backend/tests/test_api_ticket_lifecycle.py` | `/health`, создание заявки, назначение исполнителя, смена статусов, комментарии, история, уведомления, запрет недопустимого перехода. |
| Security | `backend/tests/test_security_access.py` | Запрет неавторизованного доступа, запрет назначения вне роли, запрет чтения чужой неназначенной заявки, запрет списка заявок для роли руководителя. |
| Integration | `backend/tests/test_integration_database.py` | Применение миграций до `head`, наличие seed-ролей, пользователей, категорий и статусов. |
| Frontend | `npm --prefix frontend run build` | Проверка production-сборки React-приложения. |

## Команды

Backend-тесты запускаются из контейнера backend после старта PostgreSQL:

```bash
docker compose up -d postgres backend
docker compose exec backend pytest
```

Frontend-сборка запускается из корня репозитория:

```bash
npm --prefix frontend run build
```

Полная локальная проверка перед CI/CD:

```bash
docker compose exec backend pytest && npm --prefix frontend run build
```

## Ограничения

Backend-тесты используют текущий `DATABASE_URL`, применяют миграции и очищают таблицы заявок, истории, комментариев и уведомлений до и после тестов. Справочники и seed-пользователи сохраняются.

Frontend-проверка на этой итерации ограничена production-сборкой. E2E-проверку полного пользовательского сценария через Playwright или аналог стоит добавить перед финальной приемкой.

Автоматическая проверка отсутствия секретов в логах пока не реализована. Этот пункт связан со структурированными логами и закрывается в следующем цикле вместе с итерацией 6.
