# Итерационный план разработки системы внутренних заявок

## 1. Назначение документа

Документ описывает поэтапный план реализации прототипа веб-системы внутренних заявок медицинской организации и DevOps-модели ее непрерывной поставки.

Исходный общий план проекта: `devops-ticket-system-plan.md`.

Цель итерационного плана - разбить общий объем работ на понятные циклы, где для каждой итерации определены:

- цель;
- ожидаемый результат;
- зоны ответственности;
- основные задачи;
- критерии готовности;
- артефакты для программного проекта и магистерской работы.

План ориентирован на MVP, достаточный для защиты магистерской работы, с отдельным выделением демонстрационных улучшений.

## 2. Общая логика итераций

Проект рекомендуется выполнять не как одну большую разработку, а как серию коротких завершенных итераций. Каждая итерация должна давать проверяемый результат: работающий модуль, тест, документацию, схему, пайплайн или демонстрационный сценарий.

Предлагаемая последовательность:

| Итерация | Название | Главный результат |
|---:|---|---|
| 0 | Подготовка и уточнение рамок | Зафиксированы границы проекта, MVP, роли и репозиторий |
| 1 | Базовая архитектура и инфраструктура | Создан каркас backend, frontend, БД и Docker Compose |
| 2 | Пользователи, роли и авторизация | Реализована аутентификация и разграничение доступа |
| 3 | Жизненный цикл заявок | Реализовано создание, просмотр, назначение и статусы заявок |
| 4 | История, комментарии и уведомления | Добавлены комментарии, аудит и mock/MAX-уведомления |
| 5 | Тестирование и качество | Покрыты ключевые сценарии unit, API и integration-тестами |
| 6 | CI/CD и контейнерная поставка | Настроен пайплайн проверки, сборки и smoke-теста |
| 7 | Отчеты, SLA и демонстрационный плюс | Добавлены статистика, SLA и seed-данные |
| 8 | Документация и магистерская работа | Подготовлены проектные артефакты и главы работы |
| 9 | Финальная приемка и демонстрация | Система проходит полный демонстрационный сценарий |

## 3. Роли и зоны ответственности

В рамках учебного проекта один человек может выполнять все роли, но разделение ответственности нужно сохранить для управляемости проекта и описания DevOps-процессов.

| Зона ответственности | Содержание работ |
|---|---|
| Аналитика | Требования, роли пользователей, сценарии, критерии приемки |
| Backend | REST API, бизнес-логика, авторизация, заявки, статусы, уведомления |
| Frontend | Веб-интерфейс, формы, списки, фильтры, кабинеты ролей |
| База данных | Модель данных, миграции, связи, seed-данные |
| DevOps | Docker, Docker Compose, CI/CD, переменные окружения, smoke-тест |
| QA | Unit, API, integration, smoke и security-тесты |
| Безопасность | RBAC, секреты, запрет медицинских данных, аудит действий |
| Документация | README, OpenAPI, схемы, описание архитектуры, главы магистерской |

## 4. Итерация 0. Подготовка и уточнение рамок

### Цель

Зафиксировать границы проекта, обязательный MVP, демонстрационный плюс и структуру будущего репозитория.

### Зоны ответственности

| Зона | Ответственность |
|---|---|
| Аналитика | Уточнить пользователей, роли, основные сценарии и ограничения |
| Документация | Оформить краткое описание проекта и MVP |
| Безопасность | Зафиксировать запрет на обработку медицинских данных пациентов |
| DevOps | Определить базовую структуру репозитория и окружений |

### Основные задачи

1. Зафиксировать рабочее название проекта.
2. Определить роли: сотрудник, исполнитель, администратор, руководитель.
3. Выделить обязательный MVP и демонстрационный плюс.
4. Описать границы: система не является медицинской ИС и не хранит данные пациентов.
5. Выбрать технологический стек.
6. Создать структуру репозитория.
7. Подготовить первичный `README.md`.
8. Создать `.gitignore` и `.env.example`.

### Критерии готовности

- Есть описание цели проекта.
- Есть список ролей и ключевых сценариев.
- Есть список обязательных функций MVP.
- Зафиксировано, что полноценный кабинет руководителя относится к демонстрационному плюсу вместе с отчетами и статистикой.
- Есть запрет на хранение медицинских данных пациентов.
- Есть базовая структура репозитория.
- Реальные секреты не попадают в репозиторий.

### Артефакты

- `README.md`;
- `.gitignore`;
- `.env.example`;
- краткое описание MVP;
- раздел магистерской работы с постановкой задачи и границами проекта.

## 6. Итерация 2. Пользователи, роли и авторизация

### Цель

Реализовать вход в систему, пользователей и базовое разграничение доступа по ролям.

### Зоны ответственности

| Зона | Ответственность |
|---|---|
| Backend | API авторизации, JWT, проверка ролей |
| Frontend | Экран входа, хранение сессии, защищенные страницы |
| База данных | Таблицы пользователей, ролей и профилей |
| Безопасность | Хеширование паролей, срок жизни токенов, защита закрытых API |
| QA | Проверка сценариев входа и запрета доступа |
| Документация | Описание ролей и матрицы прав |

### Основные задачи

1. Создать модель пользователя.
2. Добавить роли: сотрудник, исполнитель, администратор, руководитель.
3. Реализовать вход по логину и паролю.
4. Настроить хеширование паролей через `bcrypt` или `argon2`.
5. Реализовать выдачу JWT.
6. Добавить middleware проверки авторизации.
7. Добавить middleware проверки ролей.
8. Создать экран входа на frontend.
9. Скрывать или блокировать разделы интерфейса по ролям.
10. Подготовить тестовых пользователей.

Полноценный интерфейс административного управления пользователями и ролями не входит в обязательный MVP. Для демонстрации используются seed-данные или административный скрипт. UI/API управления пользователями можно реализовать как демонстрационный плюс.

Роль руководителя фиксируется в модели доступа, но полноценный кабинет руководителя относится к демонстрационному плюсу вместе с отчетами и статистикой.

### Критерии готовности

- Пользователь может войти в систему.
- Неавторизованный пользователь не получает доступ к закрытым API.
- Пользователь видит интерфейс согласно своей роли.
- Пароли не хранятся в открытом виде.
- JWT имеет ограниченное время жизни.
- Тестовые пользователи для ролей создаются через seed-данные или административный скрипт.

### Артефакты

- таблицы пользователей и ролей;
- API авторизации;
- экран входа;
- middleware RBAC;
- seed-пользователи;
- матрица ролей и прав.

## 7. Итерация 3. Жизненный цикл заявок

### Цель

Реализовать основной функциональный контур: создание, просмотр, назначение и изменение статуса заявки.

### Зоны ответственности

| Зона | Ответственность |
|---|---|
| Backend | Tickets API, бизнес-правила статусов, назначение исполнителя |
| Frontend | Форма заявки, списки заявок, карточка заявки |
| База данных | Таблицы заявок, категорий, приоритетов и статусов |
| Безопасность | Ограничение доступа к чужим заявкам |
| QA | Ручная API-проверка основных сценариев; автоматизированные API-тесты выносятся в итерацию 5 |
| Документация | Описание жизненного цикла заявки |

### Основные задачи

1. Создать таблицы `tickets`, `ticket_categories`, `ticket_statuses`.
2. Реализовать создание заявки сотрудником.
3. Добавить предупреждение о запрете ввода данных пациентов.
4. Реализовать просмотр своих заявок.
5. Реализовать просмотр всех заявок для администратора.
6. Реализовать просмотр назначенных заявок для исполнителя.
7. Реализовать назначение исполнителя администратором.
8. Реализовать допустимые переходы статусов.
9. Запретить недопустимые переходы статусов.
10. Добавить фильтры по статусу, категории, исполнителю и периоду.

Полноценный интерфейс административного управления категориями, приоритетами и справочниками не входит в обязательный MVP. Для MVP достаточно заранее подготовленных справочников через миграции, seed-данные или административный скрипт.

### Критерии готовности

- Сотрудник может создать заявку.
- Сотрудник видит свои заявки.
- Администратор может назначить исполнителя.
- Исполнитель видит назначенные ему заявки.
- Исполнитель может перевести заявку в работу и отметить выполнение.
- Заявитель может закрыть выполненную заявку.
- Недопустимые переходы статусов блокируются.

### Артефакты

- Tickets API;
- форма создания заявки;
- список заявок;
- карточка заявки;
- таблица допустимых переходов статусов;
- сценарий ручной API-проверки жизненного цикла заявки.

## 8. Итерация 4. История, комментарии и уведомления

### Цель

Добавить прозрачность обработки заявки: историю изменений, комментарии и уведомления через mock/MAX-провайдер.

### Зоны ответственности

| Зона | Ответственность |
|---|---|
| Backend | История изменений, комментарии, NotificationProvider |
| Frontend | Лента комментариев и история заявки |
| База данных | Таблицы истории, комментариев и уведомлений |
| DevOps | Конфигурация mock/MAX через переменные окружения |
| Безопасность | Исключение секретов MAX из репозитория |
| QA | Ручная API-проверка истории, комментариев и уведомлений; автоматизированные тесты выносятся в итерацию 5 |
| Документация | Описание интеграции с MAX и mock-режима |

### Основные задачи

1. Создать таблицу `ticket_history`.
2. Создать таблицу `ticket_comments`.
3. Создать таблицу `notification_logs`.
4. Фиксировать создание заявки в истории.
5. Фиксировать изменение статуса в истории.
6. Фиксировать назначение исполнителя в истории.
7. Реализовать добавление комментариев.
8. Реализовать интерфейс комментариев.
9. Создать интерфейс `NotificationProvider`.
10. Реализовать mock-провайдер уведомлений.
11. Подготовить адаптер для реального API MAX как заменяемый модуль.
12. Сохранять результат отправки уведомления.

Входящие команды от MAX-бота, создание заявки через MAX и добавление комментариев через MAX не входят в MVP. Эти функции рассматриваются как возможное расширение после защиты.

### Критерии готовности

- История показывает ключевые изменения заявки.
- Комментарии сохраняются и отображаются.
- При создании, назначении, изменении статуса и новом комментарии создается событие уведомления.
- Mock-провайдер сохраняет событие, статус, время и ошибку при неуспехе.
- Реальные токены MAX не хранятся в коде и репозитории.

### Артефакты

- история заявки;
- комментарии;
- `NotificationProvider`;
- mock/MAX-адаптер;
- журнал уведомлений;
- сценарий ручной API-проверки уведомлений.

## 15. Минимальные критерии приемки по итогам MVP

MVP считается готовым, если выполнены следующие условия:

1. Пользователь с ролью сотрудника может создать заявку и увидеть ее в своем списке.
2. Администратор может назначить исполнителя.
3. Исполнитель может перевести заявку в статусы "В работе" и "Выполнена".
4. Заявитель может подтвердить выполнение и закрыть заявку.
5. Все изменения статусов фиксируются в истории.
6. Комментарии сохраняются и отображаются в карточке заявки.
7. Mock/MAX-провайдер получает события уведомлений и сохраняет результат отправки.
8. Неавторизованный пользователь не получает доступ к закрытым API.
9. Пользователь не может получить чужую заявку без соответствующей роли.
10. Приложение запускается через Docker Compose одной командой.
11. Backend отвечает на `/health`.
12. CI/CD-пайплайн выполняет тесты и сборку.
13. В репозитории отсутствуют реальные секреты.
