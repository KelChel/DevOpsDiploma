# DevOps Ticket System

Прототип веб-системы внутренних заявок медицинской организации с демонстрационной DevOps-моделью непрерывной поставки.

Проект разрабатывается как учебный MVP для магистерской работы. Система предназначена для внутренних технических, организационных и сервисных заявок сотрудников. Она не является медицинской информационной системой и не предназначена для хранения, обработки или передачи медицинских данных пациентов.

## Цель проекта

Создать повторяемо запускаемый прототип системы заявок, который демонстрирует:

- жизненный цикл внутренней заявки;
- разграничение доступа по ролям;
- историю действий и комментарии;
- mock-интеграцию уведомлений MAX;
- контейнерный локальный запуск;
- автоматизированные проверки и CI/CD-процесс;
- SLA, отчеты и управленческую статистику.

## Пользовательские роли

| Роль | Назначение |
|---|---|
| Сотрудник | Создает заявки, просматривает свои заявки, подтверждает выполнение и закрывает заявку. |
| Исполнитель | Просматривает назначенные заявки, берет их в работу и отмечает выполнение. |
| Администратор | Просматривает заявки, назначает исполнителей, контролирует справочники через seed-данные или административные скрипты. |
| Руководитель | Просматривает отчеты, SLA и статистику как демонстрационный плюс. |

## Целевой обязательный MVP

В целевой обязательный контур MVP входят функции, которые реализуются по итерационному плану. Этот список описывает итоговый объем проекта, а не текущую готовность после каждой итерации.

- вход пользователя и проверка доступа по ролям;
- создание заявки сотрудником;
- просмотр сотрудником своих заявок;
- просмотр всех заявок администратором;
- просмотр назначенных заявок исполнителем;
- назначение исполнителя администратором;
- переходы статусов заявки: создана, назначена, в работе, выполнена, закрыта;
- блокировка недопустимых переходов статусов;
- история ключевых изменений заявки;
- комментарии к заявке;
- mock/MAX-уведомления с журналом отправки;
- endpoint `/health`;
- запуск через Docker Compose одной командой;
- CI/CD-пайплайн с тестами и сборкой;
- отсутствие реальных секретов в репозитории.

## Текущая готовность

После итерации 9 реализованы и приняты:

- локальный запуск backend, frontend и PostgreSQL через Docker Compose;
- endpoint `/health`;
- вход пользователя, JWT и проверка доступа по ролям;
- seed-пользователи для ролей сотрудника, исполнителя, администратора и руководителя;
- создание заявки сотрудником;
- просмотр заявок с учетом роли;
- назначение исполнителя администратором;
- переходы статусов `created` -> `assigned` -> `in_progress` -> `completed` -> `closed`;
- блокировка недопустимых переходов статусов;
- история ключевых изменений заявки;
- комментарии к заявке;
- mock/MAX-адаптер уведомлений и журнал отправки;
- базовый frontend для создания, просмотра, фильтрации, назначения, смены статуса, комментариев, истории и уведомлений;
- backend unit, API, integration, smoke и security-тесты;
- команда проверки production-сборки frontend;
- CI/CD workflow GitHub Actions с backend-тестами, проверкой миграций, frontend-сборкой, сборкой Docker-образов и контейнерным smoke-тестом `/health`;
- структурированные JSON-логи backend для создания заявки, назначения исполнителя, изменения статуса, ошибок уведомлений и ошибок авторизации;
- расчет SLA по приоритету заявки;
- признак просрочки в API и frontend;
- endpoint отчета `/reports/summary` для администратора и руководителя;
- панель статистики по статусам, категориям, нагрузке исполнителей и просроченным заявкам;
- демонстрационные seed-заявки для отчетов и SLA;
- комплект проектной документации: архитектурная схема, ER-диаграмма, REST API, CI/CD, тестовая стратегия, трассируемость требований, DevOps-метрики и правила учебного хранения данных;
- финальная локальная приемка MVP и демонстрационного сценария защиты.

## Демонстрационный плюс

К демонстрационному плюсу относятся:

- кабинет руководителя с отчетами и статистикой;
- OpenAPI-оформление основных endpoint;
- расширенные security-тесты;
- расширенная проверка структурированных логов как отдельный DevOps-артефакт.

## Ограничения данных

В системе запрещено хранить:

- ФИО пациентов;
- даты рождения пациентов;
- номера медицинских карт;
- диагнозы;
- результаты обследований;
- назначения, эпикризы и иные медицинские сведения;
- любые вложения или тексты, позволяющие идентифицировать пациента.

Интерфейс создания заявки должен содержать предупреждение о запрете ввода медицинских данных пациентов.

## Локальный запуск

Для локального запуска нужен Docker с Docker Compose.

1. При необходимости создайте локальный `.env` на основе `.env.example`.
2. Запустите сервисы из корня репозитория:

```bash
docker compose up --build
```

После запуска доступны:

- frontend: `http://localhost:5173`;
- backend healthcheck: `http://localhost:8000/health`;
- Swagger/OpenAPI: `http://localhost:8000/docs`;
- PostgreSQL: `localhost:5432`.

Для сброса демонстрационной базы:

```bash
docker compose down --volumes --remove-orphans
docker compose up --build
```

## Тестирование

Backend-тесты запускаются через pytest и требуют доступную PostgreSQL по `DATABASE_URL`. При запуске тесты применяют миграции и очищают тестовые заявки, историю, комментарии и уведомления.

```bash
docker compose up -d postgres backend
docker compose exec backend pytest
```

Проверка frontend-сборки:

```bash
npm --prefix frontend run build
```

Полная локальная проверка:

```bash
docker compose exec backend pytest && npm --prefix frontend run build
```

## CI/CD и поставка

Pipeline находится в `.github/workflows/ci.yml` и запускается на `push`, `pull_request` и вручную через `workflow_dispatch`.

Основные шаги pipeline:

- установка backend-зависимостей;
- базовая проверка Python-кода через `python -m compileall`;
- проверка миграций Alembic;
- запуск `pytest`;
- установка frontend-зависимостей и `npm run build`;
- сборка Docker-образов через `docker compose build`;
- запуск контейнеров в тестовом режиме;
- smoke-тест `GET /health`.

Секреты передаются через защищенные переменные GitHub Actions. Реальные значения `JWT_SECRET_KEY` и `MAX_BOT_TOKEN` не должны записываться в workflow, `.env.example`, README или логи. Для учебного CI используется mock-провайдер уведомлений.

Демо-стенд вынесен в отдельную конфигурацию окружения `deploy/demo/`. Это отражает промышленный подход: ветка хранит состояние кода, а окружение описывается отдельными deployment-файлами и переменными. Инструкция по запуску публичного стенда находится в `deploy/demo/README.md`.

Откат в учебном режиме выполняется возвратом к предыдущему успешному commit/tag и повторной сборкой образов. В промышленном варианте тот же процесс расширяется публикацией версионированных Docker-образов в registry и переключением deployment на предыдущий тег.

Backend пишет структурированные JSON-логи. В логах фиксируются только технические идентификаторы и статусы; названия, описания и комментарии заявок не логируются, чтобы исключить попадание чувствительных или медицинских данных.
